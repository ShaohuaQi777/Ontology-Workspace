# Ontology Workspace 工具工作台设计

状态：用户已于 2026-11-10 批准设计并要求开始 A0。本文中的 V1 范围提案随设计获批；设计批准不代表技术探针或验收已经通过。

## 1. 意图与范围

从零构建面向企业项目交付人员的本体工作台。使用者在一个自建前端中完成项目配置、接入、建模、映射、知识抽取与审核、构图、验证、发布、部署和回滚。工作台使来源、运行、审批与制品相互关联，支持可复现交付。

用户已经确认：
- 不参考、迁移或修改旧 PoC；不再要求 C01 基线和旧 CSV 隔离。
- 语义后端逻辑使用 Semantica；React 前端完全自建，不复用 Semantica Explorer。
- 只开发工具，不开发场景模拟、制造业案例、故障规则或业务金标。
- 采用独立模块化单体及先完成 A0 的推进方式。
- 接受 Python 3.12、FastAPI、React/TypeScript、SQLite 开发基线、PostgreSQL 交付配置、Oxigraph 独立远端服务、项目级本地账户与最小 RBAC、Docker Compose 优先的建议方向。
- 开发成果同步到 https://github.com/ShaohuaQi777/Ontology-Workspace.git 。

## 2. 目标、非目标与失败条件

### 2.1 工具目标

支持项目和工作区、版本化本体与制品、CSV/JSON/SQLite/PDF/DOCX 接入、字段映射、候选断言审核、实体对齐建议、语义图构建、RDF/OWL 与 SHACL 验证、用户提供的业务问题和规则执行、冲突证据管理、版本回归、审批、不可变发布、文件及远端 RDF 部署、健康检查与回滚、操作审计和安装恢复。

提供外部 Scenario Pack 的契约、校验、导入及验收运行工具，但不制作 Pack 业务内容。测试可以使用最小的领域无关技术夹具，例如资源 A/B、必填属性和两个版本；夹具仅测试软件行为，不宣称为场景模拟或业务金标。正式用户场景由外部提供。

### 2.2 非目标

不训练模型，不识别原始视觉/声学媒体，不保存全部高频遥测，不构造制造业 C01–C06，不生成 30 项制造业问题，不支持所有数据库/云平台，不建设通用 Agent 平台，不提供多租户计费或生产级分布式调度，暂不接企业 SSO。

### 2.3 失败条件

用静态轨迹伪装真实运行、把未审核抽取结果直接发布、为通过测试修改外部金标、把 Semantica 接口故障静默替换为自建语义算法、凭据进入日志或发布包、没有健康检查与回滚却宣称部署成功，均视为失败。

## 3. 路线与取舍

1. 选定：独立模块化工作台 + Semantica 语义后端。前端围绕交付流程自建；FastAPI 提供治理与编排；语义功能委托给固定版本 Semantica。优势是清晰边界和完整交付治理，代价是前端和治理模块需要开发。
2. 未选：扩展 Semantica Explorer。可能节省部分界面工作，但用户明确要求完全自建前端，且审批、项目、发布等模块与其内部状态耦合风险需要额外验证。
3. 未选：只做 CLI/API。适合先期探针，但无法满足交付人员独立操作工作台；CLI 仅作为测试与运维入口。

## 4. 后端责任边界

### 4.1 Semantica 负责的语义逻辑

接入与解析、实体/关系/事件抽取、规范化和实体对齐、知识图构建、本体候选生成与语义编辑能力、验证、推理、冲突发现、来源追溯、语义格式导出。实际可用 API 以 A0 固定版本的本机实测为准，不能把主分支文档当作能力证明。

Adapter 是接口翻译而不是另一套引擎。内部对象和异常不能越界；输入与输出使用平台 DTO，包含 run_id、来源引用、后端版本、参数摘要和结果制品。平台不散布 Semantica 调用。

### 4.2 自建平台负责的交付逻辑

项目、工作区、身份权限、制品持久化、来源登记、映射配置与确定性字段转换、候选人工审核、执行状态机、版本与差异、审批与质量门禁、哈希清单、发布包封装、部署编排和审计。这些是 Semantica 的外围治理，不替代其语义功能。

RDFLib 可用于平台格式读取、技术校验、差异或测试；不得把它的直接构图/推理实现伪装成 Semantica 结果。SHACL 等第三方能力优先通过 Semantica 已验证入口调用。若目标版本没有本体 CRUD/验证所需 API，A0 明确记录缺口并提出扩展 Adapter 或上游贡献方案，等用户确认，不自行重写语义引擎。

### 4.3 稳定接口

SemanticBackend 暴露 ingest、parse、extract、normalize/align、build_graph、import/edit_ontology、generate_ontology、validate、reason、detect_conflicts、export 等操作与 capability 查询。接口扩展记录 ADR 并有契约测试；不以最初九个方法限制必要的工具能力。

Fake Backend 只用于单元/契约测试，绝不用于产品页面或正式验收。真实 Adapter 与 Fake 使用相同 DTO 和状态契约，但仅真实执行可证明 Semantica 支持能力。

Semantica 不可用时允许浏览项目、历史版本、制品和原始文本草稿，以及管理审批元数据；需要 Semantica 的操作显示不可用及明确错误，不静默降级。离线发布包浏览/哈希校验不需要语义后端。正式发布必须有指定快照的真实验证证据。

### 4.4 V1 本体与推理范围（实现者提案，随本文批准）

可视化编辑最低范围：命名类、对象/数据属性、类和属性层级、domain/range、标签/注解与 SKOS 术语，以及 SHACL 必填、类型、基数、枚举约束。层级循环检查属于工具校验，不宣称完整 OWL 一致性判定。TTL、RDF/XML、JSON-LD 导入导出必须保留所有导入三元组（按图同构比较，含空白节点），不能只保留 UI 可编辑部分。

匿名表达式、OWL restriction、等价/互斥与其他复杂公理可原文查看/修改，但不承诺 V1 的可视化向导或完整 OWL DL 推理；UI 显示未覆盖特性而不删改。owl:imports 只登记，V1 不自动下载导入闭包；缺失依赖明确报告，不能声称验证覆盖了外部公理。原文编辑后的解析与语义操作经 Adapter 对应 capability 执行；缺少所需能力仍按 A0 缺口处理。

最低推理范围为版本化、有限、正向、非递归的确定性规则：规则 JSON 由 ID、版本、适用有效期、三元组模式前提和结论组成。变量必须在前提绑定，谓词/类型和值必须使用明确 URI/字面量；不支持存在量词创造无限资源、否定、脚本、自定义函数、SWRL 或递归。规则依赖环检测后拒绝执行。Adapter 翻译到固定版本 Semantica 经实测的原生规则接口，由 Semantica 执行，不自建推理引擎；所需原生语义不支持时作为 G0 缺口回报。自然语言规则仅作元数据，不能自动转为已批准的可执行规则。

推导事实与人工审核后的源断言分开存储，携带规则版本、前提事实引用和运行来源。查询明确选择 asserted、inferred 或 combined 视图，默认 combined 为当前构建快照的源断言与已验证推导事实集合，并在结果显示视图。门禁检查对应同一快照的源断言/推导事实及必要约束，推理失败或推导来源缺失阻断发布。Release 分别封存 asserted 与 inferred 制品；远端分别部署到版本 named graph，并由部署清单声明 combined 查询的数据集。核心查询只承诺只读 SPARQL SELECT/ASK，不运行 UPDATE、SERVICE 或任意外部读取。

## 5. 架构与数据组织

模块化单体：domain / application / infrastructure / api。基础设施包括 Semantica Adapter、元数据 Repository、制品存储、任务 Worker 和部署目标 Adapter。

元数据 SQLite 用于本地开发；PostgreSQL Compose 配置用于交付演练，迁移在两种数据库测试。制品目录保存原文、解析结果、版本快照、发布包和报告，使用内容哈希；保留兼容 S3 的接口但不承诺 V1 完成 S3 实现。图数据是审核后事实、聚合事件和来源关系，原始媒体只登记 URI/哈希及外部分析结果。

TBox、ABox、映射、SHACL、规则、验证集分别持有不可变 revision。workspace_revision 统一引用这些版本。图构建和验证对明确的 workspace_revision 执行，期间编辑只产生新版本。发布绑定图构建、规则、来源、审核和验证版本，避免旧报告用于新草稿。

关键对象：Project、Workspace、SourceConnection、SourceArtifact、OntologyArtifact、MappingSpec、CandidateAssertion、ReviewDecision、PipelineRun、GraphBuild、ValidationSuite/Run、ConflictCase、ChangeSet、Approval、Release、DeploymentTarget/Run、ExternalPackImport。

P0–P8 扩展对象：CertificationRecord、DependencyRevision、DataScopePolicy、QueryRequest/Plan/Result、SourceSnapshot、ManufacturingTemplate、TimeWindowArtifact、HypothesisEvidence、PluginManifest/Signature。这些对象分别在认证、查询、行业扩展与安全波次实现，不全部塞入 A0。

审核保留原候选和独立决策。接受、拒绝、修正均记录操作者和时间；只有当前版本接受的断言参与正式图构建。冲突保留双方证据，处理决策不删除原断言。

## 6. 持久化任务与运行中心

V1 采用单应用实例、单 Worker 的持久化任务表，不宣称分布式安全。任务包含状态、步骤、输入版本、幂等键、心跳、错误、输出和后端版本。API 创建任务并返回 run_id；前端轮询真实任务/事件记录。

Worker 对任务原子领取、步骤检查点、重试次数和恢复状态负责。进程异常后未完成任务标记 interrupted；只有无外部副作用或有幂等证明的步骤自动恢复。部署不盲目重试。取消在步骤边界生效；阻塞语义调用标记 cancellation_requested，不宣称即时终止。结果写入必须检查输入快照和取消状态。

## 7. 前端工作区

自建 React + TypeScript + Vite，通过版本化 API 读取实际状态。

- 项目入口：列表、创建向导、命名空间、语言、存储配置和概览。
- 数据接入：连接/文件登记、抽样预览、来源片段和权限范围。
- 本体工作室：类与属性树、关系图、属性面板、标签/术语搜索、原文编辑与差异。
- 映射与审核：字段映射、转换预览、候选队列、来源证据、接受/拒绝/修正。
- 运行中心：步骤状态、参数、日志、取消、重试和结果制品。
- 验证与冲突：结构/SHACL/用户问题/规则/回归结果、双方证据和处理记录。
- 发布与部署：快照、审批、门禁、制品清单、部署计划、健康检查及回滚。

导航按“项目 → 接入 → 建模/映射 → 审核/构图 → 验证 → 发布/部署”组织；当前项目始终可见。页面必须区分空状态、运行中、权限拒绝、后端不可用和真实失败。不存在数据时显示空状态，不自动添加制造业演示内容。失败提供 run_id、资源定位和可操作建议。

## 8. 接入安全与外部包契约

V1 支持文件上传和只读 SQLite 来源，数据库连接范围由用户明确指定。不执行源包脚本，转换映射使用白名单表达式，不使用 eval。路径必须在授权来源根目录内，限制扩展名、大小、解压总量和压缩比，拒绝路径穿越、符号链接逃逸、外部实体以及脚本内容执行。

外部 HTTP 来源和部署目标限制协议/地址，防止任意 SSRF；确需内网部署由管理员显式配置许可，不开放任意 URL 转发。源系统秘密只用环境变量或 Secret Provider 引用，不出现在普通 DTO、日志、URI 查询参数、报告和制品中。

建立四项共享契约：scenario-pack.schema.json、semantic-backend.openapi.yaml、validation-result.schema.json、release-manifest.schema.json。Pack YAML 解析为 JSON-compatible 对象再做 Schema 校验；各路径解析后验证 containment 与必要文件存在。规则/查询仅允许支持的声明式格式；SPARQL 禁止 SERVICE 和任意远端读取。major version 决定兼容边界。

本项目仅提出并测试契约版本，不宣称已与不存在于当前会话的场景工作线共同冻结。

## 9. 身份与审核门禁

项目级本地账户，角色为本体工程师、交付顾问、领域专家、管理员、负责人。后端每个项目操作检查授权，隐藏按钮不算权限控制。语义候选审核与发布审批分别记录，发布审批要求负责人角色；部署/回滚要求管理员。

首个管理员在本地初始化命令中创建，凭据由操作者在自己的环境配置，不通过聊天索取或保存。密码仅保存安全哈希；登录会话使用安全 cookie、CSRF 防护、失效与登录限流。实际依赖与机制在实现计划中细化。

正式发布默认阻断：待审核候选、未处理阻断冲突、阻断级验证失败、用户指定核心查询失败、来源缺失、回归破坏或快照不一致。必过门禁不可豁免；非阻断警告可以具名记录理由。没有验证集的草稿不能被宣称为完整验证的正式版本。

## 10. 发布、部署与回滚

Release 为不可变目录和清单，包含本体、约束、映射、规则、审核与来源索引、图、验证结果、依赖版本、哈希、审批和部署说明。使用临时目录生成、校验、原子封存；既有 release_id 不覆盖。清单哈希用于完整性校验，不称为密码学签名。

本地文件部署：写入版本目录并原子切换 active 指针，运行哈希、解析和指定核心查询 smoke test；失败恢复上一指针。

远端采用独立 Oxigraph 服务，使用 SPARQL HTTP 与每个 Release 独立 named graph。先 dry-run 检查目标许可、清单、查询能力和输入，随后上传新 named graph、验证数据与健康查询，最后更新平台部署活动指针。工作台查询通过部署版本选定 graph；不承诺任意第三方默认图查询会自动切换。规则、Shapes、元数据和 ABox 放到明确的 graph/制品，查询数据集约定写入部署清单。

失败不覆盖旧 graph；成功回滚切换到上一个已验证版本，并再次进行健康/核心查询检查。旧版本保留直至显式维护策略删除。凭据由 Secret Provider 解析，发布包只有引用和脱敏目标标识。服务器备份包括元数据、制品、发布包及远端图/活动版本信息；恢复在空环境演练。

## 11. 工具验收

验收以领域无关技术夹具和用户提供输入为准，不以制造业场景完成度为准。

- 创建项目、保存文本草稿、提交版本、显示差异及恢复保存点。
- CSV/JSON/SQLite/PDF/DOCX 真实接入与来源预览；解析、抽取分别显示 capability 和运行证据。
- 固定 Semantica 真实 Adapter 可运行的接入、解析、KG、本体、验证和 provenance 最小样例；不以 Fake 通过代替 G0。
- 本体核心语义导入导出往返、编辑与映射、审核拒绝和修正、未审核事实不入正式图。
- SHACL 正反例、用户定义查询、规则和冲突证据、回归失败阻断。
- 同一输入/版本在确定性步骤重复运行一致；LLM 步骤保存原始输出、参数与审核，不要求重新采样完全一致。
- 失败发布拦截、不可变制品哈希、一次文件与一次 Oxigraph 服务部署、失败恢复、成功回滚。
- RBAC、秘密泄露、上传/包路径安全、重启恢复；干净环境安装和备份恢复。
- 前端组件/API 集成/E2E 使用真实服务和真实任务轨迹；Fake 仅在明确标记的测试范围使用。

没有外部正式业务包时，报告“工具验收通过/未通过”，不能报告原草案 M6 制造业正式场景交付或 30 项业务问题通过。

## 12. 推进与 GitHub

先 A0（技术基线与契约），再项目/制品/身份基础、接入与审核、本体与映射、验证与冲突、发布部署、运维收口。身份与安全基础在最初 API 建立时实现，不拖到发布后。

A0-01 调整为新仓库初始化、忽略规则和任务基线。A0-02 实测 Semantica 安装/API/能力；0.8.0 仅是已读取主分支配置的候选，最终版本/commit/依赖来自探针。A0-03 锁文件与干净安装；A0-04 ADR；A0-05 四项共享契约与正反例。

本地项目拟建在当前工作区的 Ontology-Workspace 子目录，本文设计批准后迁入该项目 docs/superpowers/specs。仓库 main 保存基线，功能工作隔离在分支/工作树。逐任务测试、审查、单一职责提交，提交包含任务 ID，进度采用 TODO/IN_PROGRESS/REVIEW/DONE/BLOCKED。

通过检查后普通 push 到用户指定 remote；不强推、不修改全局 Git 设置、不上传秘密/运行数据/第三方仓库。如果认证不可用，保留本地提交并报告同步受阻，使用用户本机 GitHub 登录方式而非在聊天索取令牌。

进入下一高风险波次等待门禁确认。每波报告任务、文件/架构影响、可复现命令及实际结果、运行入口/截图、已知限制、待确认依赖；不虚报通过。

## 13. 已核实的本机工具环境

## 14. 留给实现者的细节与需要升级的决策

## 15. P0–P8 企业工具扩展

用户于 2026-11-10 要求将以下内容纳入开发计划。总体任务、依赖、验收见 [P0–P8 总体开发计划](../plans/2026-11-10-ontology-workspace-roadmap.md)，A0 的 P0 实现任务见 [A0 实施计划](../plans/2026-11-10-ontology-workspace-a0.md)。这些是开发范围与验收安排，不代表代码已实现或门禁已通过。

### 15.1 P0 企业适配层优先

A0 除原生探针、固定版本、ADR 与四项契约外，增加统一 SemanticBackend Protocol、稳定 DTO/错误、真实 SemanticaBackend、测试 FakeBackend、Ingest/Parse/Extract/KG/Ontology/SHACL/Reasoning 同一共享契约及版本升级兼容性执行器。对象和异常递归检查，防止内部 native 类型泄漏。升级在隔离环境对比，不改变当前生产 lock；未来版本未经实测不能宣称兼容。

### 15.2 P1/P2 工作空间与企业数据治理

项目模板、命名空间、TBox/ABox/SHACL/规则/词表分层，草稿与 ChangeSet、分支/三方差异合并、可视化概念关系属性编辑、zh-en 标签与术语、离线外部标准本体复用和候选对齐均进入工具路线。语义冲突不可只用文本自动合并；任何改变认证内容的合并产生新 revision。

映射治理包括字段、值转换、枚举、主数据对齐、文档实体/关系/事件、来源片段、模型版本/置信度、批量接受/拒绝/修正和失败重放。replay_of 与新 run_id 绑定旧输入快照，原失败和候选不覆盖。接受不等于专家认证；未知置信度用 null，不填 1.0。

### 15.3 P3 认证与发布门禁

Certification 状态为 DRAFT（自动生成或人工草稿）、REVIEWED（交付检查）、CERTIFIED（专家确认）、PUBLISHED（进入正式 Release）、DEPRECATED（停止新使用）、REJECTED（保留拒绝原因）。适用于概念、关系、属性/术语、规则、映射、抽取结果和冲突处理策略。人工操作带 actor/role/object_id/revision/dependency_refs/reason/evidence；生成器只能生成 DRAFT。

内容 revision 不可变，认证是附属记录，PUBLISHED 来自成功发布引用而非手动切换。内容或依赖改变产生新 DRAFT，不能复用旧 CERTIFIED。REJECTED 修订不抹除拒绝历史；DEPRECATED 不篡改旧 Release。实际发布所用治理对象须 CERTIFIED；实际事实须有审核，需专家确认的抽取对象须认证。旧快照证据、失效认证、仅 REVIEWED 或模型自称“已认证”均不能过门禁。

### 15.4 P4 验证/冲突与 P5 联合交付

验证中心补用户 CQ/SPARQL 金标、规则覆盖率、无答案、数据/规则/版本/时序/粒度五类冲突、发布前后回归、定位与修复建议。finding 指向概念/来源的具体 revision，跳转检查项目权限；修复生成待审核 ChangeSet，不自动应用。用户金标不由工具开发者生成或篡改。

联合发布包含本体、SHACL、映射、规则、词表、验证与认证报告、依赖版本、哈希与审批；dry-run、健康检查、核心 Smoke Test、上一版回滚和交付报告作为必要出口。当前首远端仍 Oxigraph；GraphDB/Neo4j 是新增 Adapter 的后续路线，Neo4j 属性图转换必须明示 RDF/OWL 语义差异，不直接称无损。

### 15.5 P6 制造业专用工具，不做场景模拟

提供 ISA-95 风格层级、ERP/MES/SCADA/QMS/CMMS 可配置映射模板，产品/批次/工艺版本/刀具/部件/人员关系，时序趋势/异常/状态窗口，故障假设与支持/反向/缺失证据，规则适用范围/有效期，维修前后、质量到订单风险的关联视图，以及多模态派生 JSON 映射。模板元数据需版本和人工认证，不能自动被当成企业专家结论。

只实现模板 Schema、编辑/认证、聚合与映射接口和关联/证据工具，不制作制造业案例、模拟数据或业务金标。事实、检查结果与具体因果由用户/外部输入；缺失关系和证据明确不可回答，不能自行补写根因。时序聚合是确定性源数据转换，Semantica 负责语义构图/推理；原始高频数据与媒体仍留在来源。

### 15.6 P7 SQL/知识图谱双查询

用户问题经 SQL/SPARQL/图遍历/混合路由、answerability 检查、查询生成、字段/关系/过滤值及权限验证、受控执行，返回答案、实际查询、来源和推理路径。SQL 在源系统计算大量业务数据，图服务关系/规则/来源；映射和认证模型负责 grounding，不把源表全量转 RDF。

先承诺只读 SQLite/PostgreSQL、SELECT/ASK 与有界图遍历；更多方言在独立探针后扩展。生成和语义路由优先 Semantica；如能力缺失，提供显式查询入口并报告自动生成缺口，新增生成后端另行确认，不默认接 Auto Ontology/NIM。模型和源数据对外发送必须由用户明确配置，不因“自动查询”放宽权限。

SQL AST 校验、只读数据库账号/事务、参数化值、单语句、表列 allowlist、超时/行数/跳数上限；SPARQL 禁 UPDATE/SERVICE。权限在目录、生成、执行、结果、缓存、解释各阶段一致，deny 优先。无模型条件、无权限、空集和执行失败分别报告。混合查询记录各源时点与图版本，不具备原子跨源快照时标记 best_effort。

### 15.7 P8 前置安全与企业运行

项目 RBAC、可信会话、SecretProvider、行列权限、持久化任务/run_id/失败恢复、Pipeline/审计日志、离线安装、备份恢复、插件版本/签名与内部网络信任边界贯穿开发。P0 先建立 DTO/秘密边界，P1 的首个 API 实施授权，P2/P7 的数据权限不能等到最后。

统一 SourceConnectionRegistry，接入和查询使用同一授权配置；秘密只保存引用。SecretProvider 缺失/部分配置或不可用时拒绝敏感配置/执行，不回退明文 JSON。API 不接受客户端伪造身份 header，Worker/数据库/图服务不裸露公网上；私网隔离是纵深防护，不替代身份校验。插件先为声明式包，manifest 签名/可信 key_id/SDK 版本/哈希检查失败拒绝加载；签名不是执行任意代码的安全保证。
